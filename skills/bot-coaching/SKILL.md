# Bot 调教

用户要求调教、校准或复盘 Bot 行为时使用。完整操作见 [调教手册](../../doc/bot/BOT_COACHING_PLAYBOOK.md)；按需要读取其中的诊断、测试或教练任务模板。历史经验见 [2026-11-10 案例](../../doc/bot/BOT_COACHING_CASES_2026-11-10.md)，只能作线索，不能恢复案例里的任务。

## 开始前核对

确定用户指定的 Bot、问题和本次授权范围。已获授权的诊断、配置、复测继续执行，不因例行步骤重复询问。新外发、部署或业务操作是否执行，按当次授权和真实权限判断，不能从这份技能获得额外权限。

用 `bot_list`、`bot_get` 确认对象；需要时先通过 `tool_search` 发现工具。读取该 Bot 的职责和 `bot_coaching_get` 返回的当前契约、revision、经验台账。记录运行版本、模型选择、权限、技能策略和正在做的任务。不要在调教时切换模型或放宽权限来提高分数。

## 执行流程

1. **找第一处偏差。** 从当前可访问的对话、任务回执和 trace 定位最后正确动作与第一次偏离，保留 sessionId、消息 seq 或日志行号及时间。会话或来源不可访问时说明缺口，不改身份绕过。细查运行故障时再使用项目的 agent-home-diagnostics。
2. **先做基线。** 用独立会话完成低风险诊断，不接管忙碌 Bot 的任务。分别记录规则读取、技能加载、工具执行和产物验证，不能只让 Bot 复述 SOP。先排除模型、网络、审批和工具故障。
3. **只修对应原因。** 职责、默认机器、执行入口、完成条件进入行为契约；重复操作进入技能；稳定偏好进入合适的记忆范围；临时边界留在对应任务。通用 SOP 与机器适配分开。旧限制要查来源和适用任务，不一概解除或永久继承。
4. **保存并回读。** 在当前授权内用 `bot_coaching_save` 保存。先读取最新 revision，保留完整 lessons 与已有 checks；过期保存失败就重新读取并比较差异，不盲目重送。需要改技能时走 `skill_manage`，只改可管理的技能并保留版本证据。不直接写运行库或用文件操作绕过技能管理。
5. **验证入口。** 将本技能或实际工作 SOP 配成当前 Bot 可见的固定流程技能。每个契约最多四个，不能覆盖原有有用项。固定技能只进入允许的短名单，不自动执行，也不扩大权限。严格加载失败时使用实际可用的搜索、可见技能 ID 和策略诊断，不关闭限制。
6. **做同条件复测。** 尽量保持输入、模型、权限、工具范围与运行版本一致，使用另一独立会话。记录哪些条件变化了。先验证无副作用动作，再按授权做真实小任务。读取成功、加载成功、行为正确和完整交付分别判定。
7. **沉淀有范围的经验。** 新规则先用 candidate。记录 rule、source 和 checks，每条检查含 scenario、outcome、evidence。只有实际检查通过且来源可核对，才考虑 verified；服务只检查记录结构与最后结果，不独立证明质量。出现反例时追加检查，退回 candidate 或 retired。旧检查不删改，已有检查的规则改义时新建候选并退役旧项。
8. **交付和交接。** 报告配置差异、实际加载和工具证据、前后结果、失败与未验证项。研究看有依据的结论；开发按当前项目要求看测试、独立 review、CI 和真实合并；部署另验真实运行版本与健康。启动进程、rc=0、auto-merge 或同伴自报不能替代完整交付。

## 配置与版本缺口

接口或工具不存在时，标记当前运行版本缺少能力。若当次已授权，可先通过现有 `bot_update` 调整职责，保留变更前后记录；不要声称新契约或台账已保存。代码合并、构建成功和线上可用分开报告。固定技能不能恢复被权限策略过滤的技能，模型是否遵守仍需行为验证。

不把用户质问、临时 PID、某次 PR 状态、机器路径或模型版本变成所有 Bot 的通用规则。不发送未获授权的跨 Bot 消息，不中断原任务来完成测试。不以工具调用更少推断通用能力或长期交付成功率提高。

# 工具调用配对试点：发现与边界

日期：2026-10-19。首次试点发现 F-1，随后经 `tool-call-pairing-batch-dedup` 三条验收批准修复。下文保留修复前的反例及证据边界。

## F-1：同一批返回中的重复结果会重复写入（已修复）

检查入口：`npm run test:pairing`，报告中的 `source.scenarios[name=duplicate-batch]`。修复前失败，修复后该用例保留且通过。

真实源码：`packages/agent-loop/src/runtime/tool-loop.ts` 的 `processToolResults`。
宿主接线：`packages/core/src/runtime/tool-loop.ts` 的 `hostFromDeps` 提供从有效对话读取已配对集合的回调。

反例：

1. 记录调用 a（echo，输入 token=a）。
2. 实际执行工具得到 a 的结果。
3. 向真实结果持久化函数一次提交 `[result(a), result(a)]`。
4. 有效记录变成 `call(a), result(a), result(a)`，检查器报告 `duplicate-result`，id=a。

原因：函数在批次开始时获取一次已配对集合。循环内追加第一份结果后，集合没有更新，因此第二份结果仍通过检查。分两次提交会重新读取集合，所以现有跨批去重有效。

**证据层级**：真实组件 API 的反例；探针使用内存宿主模拟同步记录。尚未证明正常 kernel 调用路径能产生重复结果数组，不声称已复现线上用户故障。即使调用方目前避免这种输入，它仍未满足本次已批准的“重复返回不产生重复结果”边界约束。

修复前模型检查通过并未覆盖这个缺陷：设计模型要求同批去重，真实实现探针显示差异，门禁正确失败。修复后更新本批已配对集合，使此处实现符合原设计模型；模型边界和验收标准均未改动。

## 修复与复核

先新增三个带验收标签的测试并确认全部失败，再修复 `processToolResults`：每次复制历史集合，每次成功追加后记入本批集合。未提供历史回调也能批内去重；不修改宿主集合，不跨批缓存，后续复用同一 ID 的新调用仍可写入。

真实源码探针及三种变异仍全部执行；源码变化首先触发 needs-review，复核映射后仅更新相关文件的指纹，并纳入新增 SDK 测试和技能说明。原反例证据 `pairing-pilot-evidence.json` 保留，修复结果见 `pairing-fix-evidence.json`。

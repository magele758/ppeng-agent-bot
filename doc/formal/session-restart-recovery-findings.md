## R-1：旧运行状态与写入占用跨进程遗留

复现示例：`model-chat-SIGKILL`、`retry-task-SIGKILL`，正常退出的对应场景也失败。

1. 第一代真实进程通过生产运行入口进入等待模型、工具执行或实际重试退避，确认阶段已到达；部分工具场景还确认已有一个结果落盘。
2. 父进程发送 SIGTERM 或 SIGKILL，等待操作系统确认旧进程退出。
3. 第二代进程用相同状态目录构造生产运行时，查询旧会话。
4. 状态/结束结果未按中断恢复一致收尾；强制终止示例仍是 `running`、无结束原因。旧重试没有自行发送请求，这项子检查通过，但旧运行状态没有正确恢复。
5. 用户明确发送新消息时，被 `WRITER_CLAIM_MISMATCH` 拒绝。保存的旧写入占用与新进程缺失的进程内绑定不一致。

相关代码：`runtime.ts` 的构造恢复只覆盖特定 Bot/子智能体路径；`stores/session-store.ts` 将占用持久化，同时把本地绑定保存在进程内；写入校验实现在 agent-loop 的 `session/writer-claim.ts`。运行中断失去执行上下文与新请求受阻是实际行为，不能靠把状态表改成绿色来消除。

## R-2：重启后的最后审批决定出现冲突

复现示例：`approval-one-chat-SIGKILL`、`approval-resume-chat-SIGTERM`、mixed/rejected 对应场景。

1. 原进程真实创建审批并停在等待状态。重启后，原审批 ID、内容、已保存决定与等待状态均保留，这些检查通过。
2. 提交最后一项决定时，审批记录和会话状态先发生更新。
3. 随后补充继续消息时遇到旧写入占用，公开决定操作抛出 `WRITER_CLAIM_MISMATCH`；读回可看到状态已经改变，等待结果仍未完成衔接。
4. 验证器记录该公开操作失败，再继续调用已有恢复入口观察后续行为；后续恢复能够执行已批准工具，不会抹去第 3 步的错误。

单项决定、部分决定持久化、全部决定已在重启前保存的窗口均独立覆盖。不能将普通“审批还在”视为“决定和恢复路径全都通过”。

## R-3：重启后取消审批，旧占用仍阻塞下一次运行

复现：`approval-cancel-chat-SIGKILL`、`approval-partial-cancel-chat-SIGTERM` 及对应终止方式。

取消能保存 aborted、清理待决审批，重复决定和再重启不会恢复原操作，这些 AC-6 检查通过。但是取消后明确发送新消息仍被旧占用拒绝，因此 AC-7 继续失败。修复不能只改显示状态，必须恢复下一次运行的实际可用性。

## 部分工具结果的边界

`partial-tools-{chat,task}-{SIGTERM,SIGKILL}` 真实执行两轮工具：a 的成功结果已保存，b 已留下受控副作用记录但未返回结果。重启后 a 保留，b 没有伪造成功或被重放；这些子检查通过。新请求因旧写入占用失败，未产生新的模型请求，因此无法证明 AC-9 要求的实际模型配对视图，门禁正确失败。

这不是“已观察到模型收到非法配对”的证据。修复旧占用后，还必须继续跑通这个端到端场景，才能判定是否存在额外的上下文修复问题。不会自动重放没有保存结果的外部操作，也不承诺跨系统恰好一次。

## 故障注入和检查可信度

- `running`：变异生产启动源码，使已有结束结果的会话变为虚假 running；基线绿色的终态任务场景新增失败。
- `retry`：变异生产启动源码，自动重新执行此前已取消的真实重试；基线绿色的取消重试场景新增失败。
- `approval`：变异生产启动源码，忘记已保存批准决定；基线绿色的部分审批场景新增失败。
- 变异经 ESM 加载器作用于当前真实产品源码的编译结果，有实际加载标记、前后源码摘要和恢复对比；不修改工作区产品文件。
- 启动失败、未知场景选择、超时、缺失报告均为 incomplete，不能报告成功。外层验证工作进程拥有独立进程组，超时硬终止时一并清理后代。
- 映射指纹覆盖生产构造、持久化、占用校验、默认内核、模型视图、验证工具与门禁。共享门禁修改先触发旧配对/生命周期的 needs-review；检查差异后只刷新两处共享文件指纹，原检查内容和标准不变。

首次终态失败夹具没有接住预期的模型失败，误记为 incomplete；修正夹具后，该终态历史场景通过。最终反例来自实际产品状态和公开操作，不将夹具错误冒充产品缺陷。

## 验证范围

这是独立 OS 子进程中的真实 RawAgentRuntime 生产构造、默认 kernel、SQLite 与 destroy 路径；模型/工具输出和 IPC 阶段观察可控，不替换恢复逻辑。每代旧进程已退出后才允许下一代打开相同数据，第三代检查幂等。报告使用逻辑进程和运行标识，随机持久化 ID 实际比较后再归一化。

没有覆盖 daemon HTTP 连接排空或调度启动链，不能宣称整个 daemon/E2E 重启已验证。也不覆盖断电、损坏存储、多进程并写、迁移、独立调度及 Bot 队列完整恢复协议或无限规模。

## 已批准修复与最终复验

四条独立修复标准已经用户确认，新增四项真实进程回归先得到 4/4 失败，再实现恢复逻辑得到全部通过。标准的 Given/When/Then 未改动，原 13 条重启标准也未删改。

- 启动恢复复用现有 `teams/fd-lock.ts` 的操作系统文件描述符锁，提供内部非阻塞获取入口；持有者仍活跃时跳过恢复，正常关闭释放自身句柄，强制终止由操作系统释放。没有新增 PID 回收、心跳监督器、环境变量或用户配置。
- 普通 chat/task 运行失去上下文后，释放旧 active WAL claim，为未配对工具补非成功的 interrupted 结果，并保存 failed/process_interrupted；阻止旧输入隐式继续。历史结果与已确认工具输出保留，未确认操作不重放。
- 有效审批暂停保留原决定、ID 和 interrupt checkpoint，包括决定已齐但尚未恢复的窗口；只清除旧进程的活跃写入占用，显式恢复时由原内核重新取得 checkpoint writer ID。审批、拒绝、取消和新的运行入口都不再被旧占用阻塞。
- Bot 队列与子智能体仍使用既有恢复协议。旧子智能体测试曾额外固定普通会话继续 running，与新批准标准冲突；现在保留原子任务 unknown/不重放、普通会话不变 unknown 的检查，并加强为普通会话 failed/process_interrupted。对应验收 YAML 没有修改。

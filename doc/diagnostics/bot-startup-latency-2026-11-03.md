## 结论

打开 Bot 记录通常不足 100ms。真正调用模型之前的长尾，主要在同步历史摘要：2026-11-03T03:10:42Z 的一个首轮 pack_turn 为 156166ms，其中 auto_compact 为 156106ms，ready 为 157189ms。

canonical Bot 的 completeText 摘要没有调用方取消信号或时间上限；自定义 summarizeMessages 同样可能永远不返回。整个 prepare_turn 等摘要结束，界面因此像是会话启动卡住。消息数达到 56 时主动摘要是既有需求，不能简单取消；历史超预算时也仍需压缩。此次不修改这些触发规则。

queue_wait 来自 Bot 工作消息排队到派送的时间，不等于 API 打开耗时。这些任务可能等待已有执行结束；本次未宣称修复所有排队问题。技能路由和电脑工具初始化是次级成本。

## 修复与边界

- canonical Bot 辅助摘要最多等待 5000ms，使用 AbortSignal 取消支持取消的适配器，并用 Promise.race 约束不遵守取消的自定义适配器。
- 超时后，同一存储中的同一会话冷却 30000ms，避免每轮重复等待。显式 force 可绕过冷却，仍受截止时间约束。
- 超时记录 summary_timeout；冷却记录 summary_cooldown。正常失败仍保留 summary_failed。
- 只有及时成功的摘要才能替换历史和归档；迟到的结果没有写回路径。原始 transcript 保留。
- 冷却仅在进程内，重启可重试；没有新增环境变量或改变用户保存的配置。
- 这是启动长尾的故障隔离，不保证上游摘要能在五秒内生成。慢模型可能更频繁跳过摘要，现有上下文预算与历史检索仍适用；未压缩原文仍在数据库中。自定义旧适配器不支持取消时，后台请求可能继续，但不会迟到写回。
- 未修改普通会话的摘要策略；未修改主回复的模型超时；未把测试时间当作生产加速数据。

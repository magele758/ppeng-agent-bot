# 本机 Lab 历史会话首屏耗时（2026-11-08）

在 23000 端口的生产构建上，用 Chrome 新建无缓存页面，进入默认 Bot。以导航开始为零点，用 DOM 观察器记录侧栏出现真实会话行、对话区出现首个消息气泡的时间。前后使用同一台机器、同一个数据库和同一个入口，没有清理历史。服务端在发布时重启过，以下是现场样本，不能单独量化每项改动的收益。

| 指标 | 修复前，3 次 | 修复后，6 次（两批） |
|---|---|---|
| 首个侧栏会话行 | 19.81、23.83、15.89 秒 | 0.81、1.03、1.04、0.39、0.84、1.04 秒 |
| 首个消息气泡 | 50.63 秒、60 秒内未观察到、43.28 秒 | 1.07、1.16、1.27、0.55、1.08、1.20 秒 |
| 浏览器摘要请求 | 8.00、9.43、4.94 秒 | 0.23、0.29、0.26、0.20、0.25、0.75 秒 |

### 延迟来自哪里

- HTML 单次约 2 毫秒，修复前通过同源代理读 68 字节健康检查也曾耗时 1.56–3.13 秒。数据库约 942 MiB，288 个会话共有 11.77 MB 元数据，单条最大 3.62 MB。最大会话有 7,879 条原始消息。普通历史分页在本机执行计划中使用会话和序号联合索引。
- 旧 daemon 约 6 秒的 CPU 采样中，复盘确认归属时读取主会话，仅 JSON 解析栈就约 1.37 秒。检查待续目标时全量读取会话，仅其中的 JSON 解析就约 1.14 秒。这些读取与 HTTP 共用主线程。95 个 Bot 中 93 个已有定义归属，可用主键检查会话存在性；历史格式仍沿用会话归属解析。
- 对每个新目标扫描所有会话，改成按父会话索引查同目标、同范围的子会话，并检查子会话是否仍在运行。四个新目标的回归样例从五次全量扫描降到一次。
- 网页选择 Bot 后，原来依次等待健康信息、包含 12 个接口的概览、历史详情。现在打开 Bot 后立即读取历史，可与概览并行。浏览器回归测试将任务列表响应一直挂起，历史正文仍可读。
- 后续独立点测中，数据库最大会话最近 50 条原始历史（约 277 KB）的五次响应耗时 16–18 毫秒。单独读取所有会话摘要仍有约 2.47 秒的长尾。摘要生成仍需加载完整会话并计算摘要 ETag，后台也仍反复解析目标快照。现场测试没有分离这两项对每次长尾的贡献。

### 日志能回答什么

PM2 有 Lab 和 daemon 的输出、错误日志。浏览器异常存入 stateDir/logs/client-errors.jsonl，支持页面、会话、构建与堆栈关联，每页最多上报 10 种异常，离线上报没有重放，服务端队列已满也会丢弃。另有 Agent 启动阶段和模型轮次事件。它们不能还原一次成功但很慢的浏览器导航。此次时序来自主动采样。常规日志缺少浏览器导航到首条正文的计时、跨代理与后端的请求关联，以及 SQLite、序列化和排队各自的耗时。下一步可在历史路径记录抽样的请求关联 ID、阶段耗时、响应字节数与构建版本，保留正文与查询内容的隐私。

### 本地中间件取舍

目前优先使用已有 SQLite 索引和前端并行读取，未部署额外服务。热缓存可用于未来多客户端反复读取同一授权视图的负载，需处理租户与用户隔离、会话变更后的失效、服务重启后的冷读。当前样本已经证明前台依赖和后台全量扫描各自造成等待，外置缓存不能直接消除这些工作。若要继续降低摘要长尾，可先把列表所需字段下推到 SQLite，分别测试首次 200 和条件读 304，再用同一负载比较引入缓存的收益。

# Bot 完整调教手册

这份手册用于把一个需要反复提醒的 Bot，调整到能在指定范围内按流程完成任务，并留下可复查的证据。这里的“调教”指配置、技能、记忆、任务边界和执行反馈的调整，不涉及模型权重训练。

先为一个 Bot 建立基线，再修第一次偏差。把有效纠正写进它实际使用的配置或技能，最后用同条件任务复测。不要把整段聊天复制给其他 Bot，也不要仅凭一次回答宣布调教完成。

项目内可调用技能为 `bot-coaching`。[接口与状态规则](COACHING.md)供查字段和限制；[2026-11-10 调教案例](BOT_COACHING_CASES_2026-11-10.md)说明本方法的证据来源和效果边界。


项目把方法保存在四个位置：`AGENTS.md` 给后续 Coding Agent 指出入口，`skills/bot-coaching/SKILL.md` 提供可加载流程，行为契约与经验台账保存每个 Bot 的配置和验证记录，自动化测试检查技能发现、严格加载和权限边界。安装或发布后，还要确认目标教练实际加载了技能。

## 1. 明确本轮要改善的行为

把问题写成可观察的动作，确定调教对象和范围。

| 模糊要求 | 可观察的调教目标 |
|---|---|
| 更主动一点 | 既有授权内测试失败后继续修复，真实受阻时记录原因和下一步 |
| 记住开发 SOP | 源码修改和 CI 修复始终通过约定的执行入口，完成后做独立 review |
| 你是 Ubuntu2 Bot | 未指定机器时连接已绑定的 Ubuntu2，不把 Mac 的结果当成远端证据 |
| 以后少踩坑 | 复现一次历史问题，验证纠正后的动作，把规则按适用范围保存 |
| 做完告诉我 | 明确什么是完成，等待真实依赖时留下可跟踪的任务或进程证据 |

一个 Bot 可以有多种能力，但本轮先选最影响结果的偏差。未绑定机器的研究或秘书 Bot，不必为诊断强加一个远端。收到只出方案的任务时，也不强行走开发流程。

## 2. 建立最小基线

先记录下列信息，再修改配置。

| 项目 | 记录内容 |
|---|---|
| 对象 | Bot ID、名称、所属组、对应会话 |
| 实际运行环境 | 服务地址、运行制品版本、主存储位置、采样时间 |
| 职责 | 当前简介、行为契约、默认机器、入口、完成条件 |
| 模型与权限 | 模型选择、权限档位、工具和技能策略 |
| 当前任务 | 正在运行、等待、失败或未完成的任务，以及本轮是否允许处理 |
| 规则来源 | SOP 名称与版本、相关记忆、用户纠正及其适用范围 |
| 基线任务 | 测试输入、允许的动作、预期行为、实际证据 |

只保存诊断和回滚需要的配置。不要整库导出历史，也不要把凭据、完整模型输入或不相关私聊附到报告里。

开发目录的提交不能证明服务正在运行该版本。多实例环境要对上实际进程、工作目录和存储。读不到时标“未验证”，不要用另一个实例补证据。

忙碌 Bot 优先使用平台支持的独立诊断会话。不要取消业务任务、重绑 canonical 会话，或把另一个会话的执行结果算到它身上。独立会话测的是规则能否迁移，原长会话中的持续执行还需要单独观察。

### 可直接使用的基线请求

```text
对 <Bot 名称或 ID> 做一次独立、只读的职责诊断。

本轮不恢复历史任务，不改文件、配置、记忆或技能，不启动开发进程，不派工或外发。
读取现有职责后，实际加载一个相关且可见的技能。
若职责已绑定机器，做一次该机器的只读身份探针。机器未知不要猜。

报告职责、默认位置、实际加载结果、工具证据、完成条件和未验证项。
把规则读取、技能加载、行为执行分别说明。
```

这段请求只限制这次诊断。它不撤销此前仍有效的授权，也不能被保存成永久“只读”规则。

## 3. 从日志找第一次偏差

沿着同一请求检查“用户输入、任务接收、规则加载、工具调用、结果处理、最终报告”。找到最后正确动作和紧接着的偏离，避免把所有问题都归为“没记住”。

| 观察到的偏差 | 优先核对 | 对应改法 |
|---|---|---|
| 名字是远端 Bot，却在本机找仓库 | 简介、机器绑定、技能正文、工具目标 | 对齐目标机，并用真实远端探针验收 |
| 知道 SOP 名字，却加载失败 | 技能可见性、同名冲突、短名单、允许清单 | 用实际目录确认 ID；配置可见的固定流程技能 |
| 已加载 SOP，仍用错工具改源码 | 加载事件与实际修改调用的先后关系 | 明确执行身份，针对违规动作复测；持续失败再补系统约束 |
| 新任务被旧“别开发”拦住 | 原指令来源、任务范围、是否被更新 | 将临时限制留在原任务，保留真正的权限边界 |
| 一直报状态，没继续修复 | 当前授权、修复预算、等待对象、可执行下一步 | 明确收口条件，检查后续动作，而不是只问进度 |
| 看见警告就放弃 | 退出状态、输出、产物、上游实际请求 | 依据完整结果判断，不用单个关键词定性 |
| 收到同伴经验却不采信 | 来源、版本、适用机器、有无本地反证 | 核对事实和适用条件；正文没写不能当作反证 |
| 经验越积越乱 | 重复规则、旧版本、任务状态混入长期记忆 | 合并有效规则，保留替代关系，退役过时项 |
| SSH、模型或审批阻塞 | 原始错误与真实权限 | 单独记录环境或系统问题，不用放宽权限换分数 |

证据记录到消息 seq 或 trace 行号，并写明时区。同伴自报属于线索；需要验收的结果要由本轮工具、原始产物或可核对回执支持。

## 4. 把纠正保存到合适的位置

| 内容 | 保存位置 | 示例 |
|---|---|---|
| 稳定职责与默认值 | Bot 行为契约 | 职责、执行位置、执行入口、完成条件 |
| 重复执行步骤 | 技能 | 开发 SOP、信息评审流程、巡检方法 |
| 长期用户偏好或稳定事实 | 对应范围的长期记忆 | 用户要求开发后独立 review |
| 当前任务的授权和边界 | 当前任务或目标记录 | 本轮只出方案、不部署 |
| 一次踩坑与改法 | 经验候选 | 某警告在特定启动方式下不代表失败 |
| PID、当次提交、PR 状态 | 任务进度和运行证据 | 某进程仍在运行，尚无结果文件 |

不要把“给你 SOP 怎么还没记住”作为操作规则保存。提炼能改变下一步动作的纠正，例如“协调者不自己改源码，后续 CI 修复仍走原开发入口”。

不要为调教增加功能开关环境变量。项目已有设置优先走 Lab 和持久化配置。

### 填写职责卡

```text
职责：<处理什么任务，交付什么结果>
默认执行位置：<机器绑定或已验证入口；未知时明确未知>
执行入口：<直接执行，还是通过指定 CLI 或协调流程>
完成条件：<可检查的产物和状态>
固定流程技能：<当前 Bot 可见的技能名称或 ID，最多四个>

临时边界另外记录到本次任务，不写成永久职责。
```

开发协调者示例：在指定机器上，通过该机器约定的 CLI 完成实现和修复；独立 review 与检查通过后，按当前项目规则推进到真实合并。研究 Bot 示例：交付有来源的结论、现有覆盖、真实缺口和下一步验证办法，不把方案当成已经实现。

### 分开通用 SOP 和机器适配

通用 SOP 写接任务、验证、review、交付和证据规则。机器适配写目标机、工具入口、目录解析和必要的连接前提。单次事故放案例，不写死某次 PID、PR、模型 ID 或临时版本。

4090 的可迁移经验是“默认目标明确、入口一致、执行证据可核对”。它的主机、WSL 路径和工具安装方式不能直接复制给 Ubuntu、Mac 或研究 Bot。

## 5. 用项目能力保存和回读

已部署调教能力的实例，在 **Bot 设置 → 概览 → 调教与经验** 保存职责卡与经验。固定流程技能让技能在普通请求的短名单中可见；它不自动执行技能，也不保证模型遵守。

通过对话操作时，先用 `bot_coaching_get` 读取配置和 `revision`，再用 `bot_coaching_save` 保存。保留全部既有经验和验证记录。工具未出现在当前列表时，先用当前可用的发现工具查找。

保存后重新读取并比较差异。若提示版本已变化，重新取最新版，合并本次确实要改的字段。不要拿旧快照重试覆盖。

技能正文通过现有技能管理流程更新。仓库技能由项目维护；Bot 自建或共享技能通过 `skill_manage` 操作。收到的只读技能不能冒充自己拥有，也不能用文件写入绕过管理。

接口或面板缺失时，先核对实际运行版本。代码合并、构建通过和线上可用是不同结果。在当前授权内可以先用现有职责管理能力修正简介，但要说明新契约或台账尚未保存。

固定 `bot-coaching` 给教练时，保留原有有用技能，并确认总数未超过四个。不要给所有开发成员强制固定这份调教技能；它主要服务教练和承担行为复盘的 Bot，工作成员继续使用自己的工作 SOP。

## 6. 用行为复测

尽量保持前后测试输入、模型选择、权限、工具范围和运行版本一致。条件无法一致时，记录变化，不能把全部改善归功于某次提示修改。

按需要选择下面的场景。先做无副作用检查，再做当前已授权的真实小任务。

| 场景 | 要观察的结果 |
|---|---|
| 普通请求不提机器 | 使用已绑定目标机，工具参数和结果能对上 |
| 用户明确换机器 | 按当次授权处理；不能把默认值当永久禁令 |
| 同义改写 | 不依赖一句固定口令才能正确选流程 |
| 新任务或独立会话 | 职责与规则能迁移，不靠原聊天上下文提示 |
| 上下文压缩后继续 | 任务边界和下一步仍正确；没测就标未验证 |
| 同伴给出旧规则 | 检查来源和适用范围，不盲从，也不无证据否认 |
| 实现或测试失败 | 在当前授权和预算内沿原入口继续修复 |
| 真实外部阻塞 | 报告原因、已完成部分和可恢复的下一步 |
| 自报完成 | 能拿出该任务要求的产物、检查和状态证据 |

分开记录四层结果：

1. 配置已保存且回读一致。
2. 相关技能已实际加载。
3. 预期工具动作确实发生。
4. 用户要求的完整交付已验收。

上一层通过不能代替下一层。`hostname` 正确，只证明这次身份探针；`rc=0` 只说明对应进程正常退出；auto-merge 已开启，也不等于 PR 已合并。

### 按任务定义完成

| 任务类型 | 完成证据 |
|---|---|
| 研究 | 可核对的来源、现有覆盖、结论与缺口；方案和实现分开 |
| 开发 | 当前要求的实现、测试、独立 review、修复及真实合并结果 |
| 部署 | 真实运行版本、目标实例、健康和用户路径验证 |
| 巡检 | 正确实例和时间范围的数据、问题证据、影响与未验证项 |
| 协调交接 | 任务确实接收、回执归属正确、产物验收完成 |
| 秘书复盘 | 原记录可追溯，已完成、进行中、阻塞和计划区分准确 |

## 7. 把一次纠正变成可复用经验

先建立经验候选，填写以下内容。

```text
规则：<触发条件和应采取的动作>
适用范围：<哪类 Bot、机器或任务；写进规则正文>
来源：<用户纠正、会话或日志位置>
反例：<什么情况下不适用；写进规则说明或关联案例>
验证场景：<准备执行什么检查>
验证结果：<passed、failed 或 blocked>
证据位置：<对应消息、trace、产物或检查回执>
```

候选的状态是 `candidate`。最后一条检查通过且证据完整时，系统允许保存为 `verified`。操作者仍要核对证据是否支持这条规则。系统不自动检查引用真实性，也不独立证明质量提升。

把验证结论限制在实际场景内。例如“这次只读身份探针正确到达 Ubuntu1”可以有工具证据；“以后一定能自主开发并合并”需要另一组真实交付验证。

出现失败时追加检查，并退回候选或标 `retired`。不要删除失败记录。已有检查的规则要改变含义时，新建候选并退役旧项，保留替代关系。

达到台账容量限制时，不要删除旧检查来过保存校验。先停止追加，整理需要归档或换版的记录，并明确当前系统的限制。字段与容量见 [接口参考](COACHING.md)。

### 分享给其他 Bot

分享规则、变更点、来源、适用条件和验证范围。接收方先做低风险的本地检查，再决定是否采纳。核验不到的部分继续标候选。

不要因为同伴描述和技能正文不同就否定事实，也不要因为同伴说“我试过了”就替所有成员改规则。跨 Bot 消息和共享配置修改仍要在用户当次授权内。

## 8. 让 Bot 教练执行同一流程

把教练设为诊断与验证角色。它管理调教证据，不接管目标 Bot 的业务任务。先确认它能管理哪些 Bot，再给它固定 `bot-coaching` 技能。需要细查运行问题时，再按需加载诊断技能。

向教练交代对象、目标、允许修改的范围和复测边界。

```text
按 bot-coaching 流程调教 <Bot 名称或 ID>。

目标：<一个可观察的偏差>。
授权：读取相关配置、对话与日志，修改本 Bot 对应的职责和流程配置，做只读复测。
保留：当前任务、权限档位、模型选择和不相关规则。

先做基线，再调整并回读，用同条件新会话复测。
需要修改共享技能时，先核对所有权和受影响成员。
有真实证据的窄范围结论才能标已验证，其余保留候选。
报告配置差异、动作证据、结果和未验证项，不以口头承诺收口。
```

若要进一步验证开发交付，补充指定仓库、目标机器、可修改范围、完成条件和修复预算。没有这些授权时，教练停在诊断与配置复测，不自行启动业务开发。

## 9. 保留一份调教记录

每轮只保存需要复查和回滚的材料。

```text
对象与时间：
问题和本轮目标：
运行实例、模型、权限和技能策略：
原配置与有效 SOP 版本：
最后正确动作与第一处偏差：
证据索引：
根因分类：
修改前后差异：
保存与回读结果：
基线与复测输入：
实际工具动作与产物：
通过、失败、受阻、未验证项：
已验证经验及适用范围：
仍为候选的规则：
回滚依据和下一步：
```

回滚前重新读取当前配置，确认没有其他有效修改。只恢复本轮变更涉及的字段，不整表覆盖运行库，不把业务任务状态回滚到旧快照。

## 10. 按真实任务继续观察

首次诊断通过后，让 Bot 执行一个当前已授权的小任务。再看一次换任务、压缩后继续或旧规则干扰的场景。需要怎样的重复验证，取决于任务成本、失败影响和变化频率，不承诺固定几轮就能训好。

分别记录定位正确率、实际流程遵守、完整交付、误报完成、人工纠正次数和环境阻塞。工具数量、耗时与成本只作为辅助指标。输入和任务不同，不能直接比较数量。

2026-11-10 的工具结果数从 85 降至 31、技能拒绝从 4 降至 0，支持的是该次同题诊断少走弯路。长期研发、CI 自修和部署质量还要单独验证。完整背景见 [案例记录](BOT_COACHING_CASES_2026-11-10.md)。

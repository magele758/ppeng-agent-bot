## HTTP soak

- 功能验证：`node --test scripts/test/bot-http-soak-harness.test.mjs`。继续检查固定输入、真实工作完成、调度、审批、故障收尾及短测不得冒充完整验收。
- 独立性能验证：先执行 `node scripts/build-workspace.mjs`，再执行 `pnpm run test:bot:soak:performance`。
- 性能执行器以独立子进程运行既有压缩负载，移除覆盖率采集环境，不继承 Node 注入参数；不改变原负载或 p95 门槛。
- 全量 Release gate 增加独立 `soak-performance` job。失败、取消、跳过或缺失均不能通过 Main release gate。本地 `pnpm run ci` 同样包含它。
- 结果保存在 `test-results/soak-performance/http-soak.json` 和 `performance.json`，CI 无论成败均上传证据。

性能门槛沿用 workload.v1：page/status/receive p95 不超过 500ms，search p95 不超过 1000ms。
缺样本、非正常结束或功能失败同样判定性能验证未通过。独立执行不意味着共享机器满足标准硬件条件。
压缩负载的性能通过也不等于完整浸泡或发布验收通过；完整发布证据要求继续有效。

## 两个 soak 阻塞的根因与修复（2026-10-21）

例行任务失败样本中的 `http_op_24` 已成功调用软件一次，产品侧例行记录为 completed，但报告没有包含该任务的完成确认。两个例行提示在同一会话并入后，压缩保留了最新提示和两条成功工具结果；受控模拟模型仍按提示查找待办，较早提示被摘要替代后就漏掉了其结果。现在只对「之前已开始、尚未确认，且当前模型输入实际含同会话成功工具结果」的操作补齐确认。失败结果、别的会话、未知操作及已经确认的操作都不能借此通过；不重放工具，不根据数据库中的副作用直接伪造完成。原本失败的压缩场景已加入回归。

接收延迟的主要 CPU 热点是技能词法路由：群聊提示约 150 个不同词，对本机 238 个技能逐一扫描正文，单次约 120ms；原采样累计约 7 秒花在这里。先缓存标准化字段和有界的逐词匹配，技能字段变更会使缓存失效，长输入不进入缓存；随后让运行时每处理 16 个技能让出事件循环，防止冷缓存扫描连续占用 HTTP 线程。同步路由接口仍保留，所有技能仍参与评分，权重、子串匹配和最终排序不变。

31 条真实慢查询与原实现逐项对照，评分、理由和顺序完全一致；原总耗时 2213ms，缓存实现首次批次 275ms、热缓存批次 109ms。单独加缓存后的两轮性能为 215ms / 657ms，第二轮失败，**这组没有计为通过**；因此进一步加入分批让出事件循环，并重新执行完整验证。中途的诊断采样不计为验收。

所有诊断和失败样本保留在 `test-results/soak-diagnosis/`、`test-results/soak-fix/`。负载、500ms 接收门槛、审批等待、收尾期限和重复调用检查均未放宽。

最终代码按预先约定连续执行两轮独立性能验证，二者都必须通过；构建指纹和负载哈希一致：

| p95 指标 | 第一轮 | 第二轮 | 原门槛 |
| --- | ---: | ---: | ---: |
| page | 114ms | 29ms | 500ms |
| search | 78ms | 27ms | 1000ms |
| status | 72ms | 34ms | 500ms |
| receive | 302ms | 95ms | 500ms |

两轮均完成 320 次测量期读取、34 项测量期工作，调度和审批通过、正常收尾，重复软件调用为 0，每项操作最多 2 轮模型处理。结果分别在 `test-results/soak-fix/final-performance-{1,2}/`，摘要为 `test-results/soak-fix/final-summary.json`。这些是压缩负载验证，不代表已完成 24 小时浸泡或标准硬件发布验收。

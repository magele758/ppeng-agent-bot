# 还没有验收规格的方向

这些条目来自路线图和计划文档，不是已经排期的承诺。路线图写明不承诺具体日期；大阶段可以并行，但没有验收规格之前都不能当成产品。安全与监管要求高于自动化，人类在环不能被这些方向绕开。

下面不重复 `acceptance/*.yaml` 里已有的规格。那些规格无论未实现还是已取消，都只出现在 [from-acceptance.md](from-acceptance.md)。

## 发布与长期运行

### 一次发布固定一组不可变版本

还不是承诺。

- 来源：[目标发布链与当前缺口](../../RELEASE_RELIABILITY_PLAN.md#2-目标发布链与当前缺口)
- 用户以后可能看到什么：一次发布被记成一组对得上的不可变版本，而不是靠两个都会变动的 `latest` 标签来证明镜像配在一起。
- 为什么还没进验收规格：计划把「两个镜像的 registry 标签更新不是原子事务」写成仍须明确的边界，并要求生产记录固定的一组不可变版本。仓库里没有对应的验收规格。

### 主干合并是否强制走发布门禁

还不是承诺。

- 来源：[目标发布链与当前缺口](../../RELEASE_RELIABILITY_PLAN.md#2-目标发布链与当前缺口)
- 用户以后可能看到什么：若远端规则确实这么设，合并进主干就不能绕开发布门禁。计划没有把这件事写成已经核对过的事实。
- 为什么还没进验收规格：计划写明这取决于远端 Ruleset 或分支保护，该轮没有修改这些设置，也没有声称已经验证。仓库里没有对应的验收规格。

### 同一版本的构建产物缓存

还不是承诺。

- 来源：[如何减少 Agent 与人工的循环成本](../../RELEASE_RELIABILITY_PLAN.md#4-如何减少-agent-与人工的循环成本)、[当前不实施的范围](../../SINGLE_HOST_COMPLETION.md#当前不实施的范围)
- 用户以后可能看到什么：同一次候选上重复的检查，可以复用这一版自己的构建产物，从而缩短门禁。另一个版本的通过结果不能拿来顶替。
- 为什么还没进验收规格：单机收尾把通用构建缓存后置。发布计划只说先记下每层耗时，再考虑缓存同一次构建的产物，并且不得削弱覆盖或复用另一版的绿灯。仓库里没有这条的验收规格。

### 发布可靠性先记账，再谈数字目标

还不是承诺。

- 来源：[如何减少 Agent 与人工的循环成本](../../RELEASE_RELIABILITY_PLAN.md#4-如何减少-agent-与人工的循环成本)
- 用户以后可能看到什么：发布失败或回滚次数、测试不稳定率、定位耗时、人工介入次数、门禁耗时，以及编码助手的修复轮数，被连续记下来。数值目标要等基线有了再定。
- 为什么还没进验收规格：计划写明先积累基线再定数值目标，并把复杂度分数只当作局部风险信号，不当总体可靠性评分。仓库里没有对应的验收规格。

## 联邦

### 没有唯一主控的节点协作

还不是承诺。

- 来源：[P3：无中心「电脑矩阵」](../../ROADMAP.md#6-p3无中心电脑矩阵)、[非目标（不做 / 远期）](../../CAPABILITY_DISCOVERY_PLAN.md#非目标不做--远期)
- 用户以后可能看到什么：多台机器对等协作。可以有小型的协调面，但它不是业务大脑。一台机器停掉，不应当让整个网络停摆，也不能变成「只有一个主控进程还在，别的机器才能工作」。
- 为什么还没进验收规格：路线图把拓扑、冲突策略和这条退出标准放在 P3。发现计划把联邦拓扑、CRDT 和多节点协调平面列为不做或远期，只把端点目录当作前导。仓库里没有联邦拓扑的验收规格。

### 节点身份与可吊销的策略包

还不是承诺。

- 来源：[P3：无中心「电脑矩阵」](../../ROADMAP.md#6-p3无中心电脑矩阵)
- 用户以后可能看到什么：节点之间能核对彼此的身份，连接可以走到双向认证；下发的策略包有签名，也能被吊销。
- 为什么还没进验收规格：路线图只列出节点身份、mTLS、策略包签名与吊销。发现计划写明不必等这一整段做完才做端点目录。仓库里没有对应的验收规格。

### 网络分开之后仍能人工接管

还不是承诺。

- 来源：[P3：无中心「电脑矩阵」](../../ROADMAP.md#6-p3无中心电脑矩阵)、[非目标与约束（现阶段）](../../ROADMAP.md#8-非目标与约束现阶段)
- 用户以后可能看到什么：节点之间暂时失联时，各自先按约定继续，之后再对齐；人仍然有通道把工作接过来。这不是绕过审批的自动网络。
- 为什么还没进验收规格：路线图把分区容忍、异步最终一致和人工接管写成 P3 的韧性要求，并写明「天网」只是架构隐喻。仓库里没有对应的验收规格。

### 分布式存储与多个 daemon

还不是承诺。

- 来源：[当前不实施的范围](../../SINGLE_HOST_COMPLETION.md#当前不实施的范围)、[P3：无中心「电脑矩阵」](../../ROADMAP.md#6-p3无中心电脑矩阵)
- 用户以后可能看到什么：状态不必绑在一台机器的一份库上，也可以有多个 daemon 一起承担协调，而不是永远只有一个实例握着全部持久状态。
- 为什么还没进验收规格：单机收尾明确把分布式存储、多 daemon 和联邦后置。多机现场规格写的是单实例持久状态，并且不把多协调器高可用算进那一阶段。仓库里没有分布式存储或多 daemon 的验收规格。

### Tailscale 上更进一步的设备操作

还不是承诺。

## 1. 目标与本次核对后的修正

目标：让一个 Agent 任务产生的变更，可以追溯到需求与验收标准，证明测试和审查覆盖当前候选，安全合入，并明确区分开发完成、合入完成与部署完成。继续使用 Git 和现有发布体系。

背景：[Anthropic — Redesigning source control at Anthropic](https://www.anthropic.com/research/redesigning-source-control)。借鉴服务化操作、不可变身份和按需计算的原则；以下工作项是结合本仓库提出的设计，不是文章的实现复刻。

本次进一步核对发现：

1. [`scripts/evolution/DEPRECATED.md`](../scripts/evolution/DEPRECATED.md) 明确自 2026-10-16 起停止维护旧 shell 自进化流水线；[`evolution-surface.ts`](../apps/web-console/lib/evolution-surface.ts) 的入口开关为 false。上一轮把旧 Evolution 当作主要改造入口不准确。本计划不恢复入口、不继续扩展旧脚本。

## 2. 当前资产、缺口与处理方式

| 能力 | 已核对资产 | 本计划处理 |
|---|---|---|
| 受控开发与远端合入 | `factory/delivery.ts`、`delivery-types.ts`、`delivery-worker.ts` | 保持现有授权和远端保护；补身份映射及跨入口回归 |
| Self-heal 本地合并 | `self-heal-scheduler.ts`、`self-heal-executors.ts` | 优先补候选验证、目标推进、共享写入及恢复语义 |
| 发布证据 | `release/quality-promotion.mjs`、`gates.mjs`、`agent-eval/quality-gate.mjs` | 接入 changeId 和合入映射，保留原有强门禁 |
| 编排记录 | `orchestrator/types.ts`、`store.ts`、daemon orchestration routes | 关联变更视图；不复制 Factory/Release 的可变状态机 |
| 设置持久化 | `discovery/settings.ts` 的 daemon_control 模式 | 复用 UI + API + 持久化；保存后生效 |
| 旧 Evolution | 停止维护的脚本及关闭的产品入口 | 只提取失败场景和只读历史，不作为新执行后端 |
| 验收体系 | `acceptance/`、JUnit、`test:acceptance` | 每个阶段规格、测试、实现一起交付 |

旧脚本提供三个回归素材：测试后 rebase 改变候选、Agent 修复合并冲突后直接提交、在主仓运行门禁却将结果用于候选。这些是设计反例，不等于当前 Factory 也存在相同问题。

## 3. 必须保持的不变量

1. 测试与审查证据绑定明确的仓库、目标分支、候选版本和验证基线；不能只记录 `passed: true`。
2. 候选、基线、测试配置或政策变化时，旧证据保留历史，但不能继续代表当前候选有效。
3. 已发布分支保持正常提交与推送，不 force push，不 rebase 已发布历史。
4. 编码和修冲突在隔离工作区完成，不能长时间占用共享主仓写入锁。
5. 同一仓库与目标的受控写入必须协调；超时本身不证明旧写入者已经停止。
6. Agent 的总结和自行编写的“通过报告”不能充当可信 runner / CI 的验证回执。摘要只能校验完整性，不能单独证明来源可信。
7. 结果未知先核对实际状态，不直接重做 push、建 PR 或合并；失败历史不能通过重跑覆盖。
8. 开发完成、合入完成、部署完成分别记录；缺少部署证据就展示“未部署/未知”。
9. 新展示与关联能力不扩大任务原有授权；Factory 原有逐任务授权、主体隔离、敏感范围和平台保护继续有效。
10. 可靠性检查不能被 UI 开关关闭。可配置的是调度、预算、保留和通知等策略。

## 4. 目标结构与最小公共契约

```text
需求 / 验收标准 / 修复任务
          ↓
Factory / Self-heal / Orchestrator（各自保留事实来源和授权）
          ↓
候选身份 + 可信测试/审查证据
          ↓
隔离集成 → 验证 → 受控交付 → 实际合入核对
          ↓
现有 Release 候选 / 镜像 / 部署门禁
          ↓
Lab 变更视图、可追溯历史、耗时与成本指标
```

首版不建立通用源码服务器。优先增加小型公共类型、校验纯函数和适配器；建议位置为 `packages/core/src/change-control/`，具体抽取边界在阶段 A 用调用链和测试确定。不新增 npm 包，不改 agent-loop SDK 契约。

### 4.1 变更身份

| 字段组 | 拟定字段 | 规则 |
|---|---|---|
| 逻辑身份 | `changeId`, `sourceKind`, `sourceId`, `principalId` | 同一需求多次修复保留 changeId；执行尝试另编号 |
| 仓库身份 | `repositoryId`, `targetRef`, `backend` | 远端使用已验证 Node ID；本地 worktree 按公共 Git 目录归一；不能仅凭 URL 字符串合并身份 |
| 候选身份 | `originalBaseSha`, `integrationBaseSha`, `candidateSha`, `candidateTree`, `attemptId` | 原始基线不覆盖，集成基线逐次记录 |
| 意图 | `intent`, `acceptanceIds`, `outcomeKind` | 描述要改善的行为，不能用文件数量代替成果 |
| 版本 | `schemaVersion`, `policyRevision` | 便于兼容和证据失效判断 |

### 4.2 验证证据

每项证据记录 `evidenceId`、候选身份、类型、可信执行来源、测试套件/命令摘要、工具链与锁文件身份、开始结束时间、结果、报告摘要和存储引用。沿用 Factory CI 的 workflow/run/attempt/job/App 核验，不降级为名称匹配。

有效性与执行结果分开：`pass/fail/error/not_run` 表示运行结果，`valid/stale/missing/unknown` 表示能否证明当前候选。第一次失败及后续尝试全部保留，按既有门禁政策判断，不能仅挑一次绿灯。

首版要求当前候选重新验证。即使 tree 相同，也不自动跨 SHA/基线复用审查或发布证据；后续缓存只能在完整输入身份和套件语义允许时复用。

### 4.3 合入与发布映射

记录 `testedSha → publishedHeadSha → mergeSha → releaseRunId → imageDigest`。squash/merge 提交 SHA 不同是合法情况，必须通过已有发布器或平台事实核对父基线、tree 及目标可达性；不能仅做字符串相等判断。

一次发布可能包含多个 changeId，一个变更也可能进入多个发布或被 revert。使用多对多关联并记录 revert/supersede，不把“最新发布”简单覆盖旧记录。

## 5. 分阶段开发与交付

### A — 基线核查、现有能力复用与反例复现（P0）

**目的：** 确定真正缺失的行为，避免给已有 Factory 再造队列与证据系统。

开发/补充项：

- 追踪 Factory、Self-heal、Release、手工 CLI 四类入口的候选产生、测试、审查、合入和恢复调用链。
- 核对现有验收规格和测试；列出哪些已有覆盖、哪些只有文档声明、哪些需现场验证。
- 在临时 Git 仓库复现三类旧脚本反例，再判断当前活跃入口是否受影响。
- 定义统一身份字段与失败分类，保留各后端的状态和权限归属。
- 记录启动、构建、测试、审查和队列耗时的已有来源；数据不足标记 unknown。

涉及：`packages/core/src/factory/`、`self-heal/`、`scripts/release/`、`scripts/agent-eval/` 及对应测试。

交付：入口矩阵、最小契约、可执行反例；发现实际缺陷时在同一个修复 PR 内完成红→绿，不合入故意失败的基线。

完成条件：每个入口都有明确“由谁验证、验证哪个版本、由谁写入、未知结果如何处理”的答案；没有把旧 Evolution 重新接入。

### B — Self-heal 候选验证与隔离集成（P0）

**目的：** 先闭合仍在使用的本地修复交付路径。

开发项：

1. 记录修复完成后的候选 SHA/tree、目标基线、测试及审查证据。
2. 在专用集成 worktree 准备最终待合入内容；测试前重建所需产物，避免旧 `dist` 被当作新代码。
3. 基线前进、冲突修复或候选发生任何变化时，重新执行必需检查；重新审查最终 diff 和关联调用链。
4. 本地落地前核对期望基线；共享主仓有用户改动时保留现场，按已有策略延期，不自行 reset/清理。
5. 成功核对实际合入 SHA/tree 后才进入后续重启请求；验证失败或结果未知不请求重启。
6. 候选失败、进程取消或预算耗尽时，保留必要代码和证据供恢复。

拟定规格：`self-heal-candidate-evidence`。

验收标准草案：

- AC-1：候选测试通过后目标出现新提交，系统重新验证集成结果，旧绿灯不直接放行。
- AC-2：冲突修复引入行为回归，系统阻止合入，并保留修复和失败证据。
- AC-3：主仓通过但候选失败，候选仍被拒绝。
- AC-4：源码更新后旧构建产物仍存在，系统验证新构建结果。
- AC-5：合入未确认或失败，系统不会宣称完成或触发成功后的重启。
- AC-6：用户工作区有改动或任务取消，已有改动和必要诊断材料保留。

测试：真实临时 Git 仓库 + 可控 runner；使用不同提交故意制造行为冲突，包括 Git 无文本冲突但测试失败的情况。不依赖真实 LLM 才能重现。

### C — 写入协调和崩溃恢复（P0）

**目的：** 让多个受控入口不会同时推进同一个目标。

开发项：

- 优先复用 Factory 的队列身份、操作意图和结果核对语义；只在本地后端确有缺口时抽取或增加协调实现。
- 本地按 canonical Git common directory + targetRef 协调；远端按已核验 repository Node ID + targetRef 协调。相互映射需显式核验。
- 明确唯一受控写入入口；其它 CLI 和 Self-heal 通过适配器进入。外部用户或第三方写入仍通过基线变化检测应对，不能宣称本地锁可锁住 GitHub。
- 修冲突、构建、测试在锁外执行；锁内只核对身份、提交操作意图、执行必要写入并核对结果。
- 在写入前持久化 operationId；重启先检查实际 ref/PR/回执，再决定重试或完成。
- 未知结果保持 verifying；不能仅因租期到时启动第二个写入者。目标反复变化时有界重试，延期保留候选，不无限烧 token。
- 本地 checked-out 分支与工作区保持一致，不能直接 `update-ref` 留下脏索引；远端仍经既有 PR/保护规则，不直接更新受保护 ref 绕过门禁。

拟定规格：`change-delivery-coordination`。

验收：双进程同目标只有一个受控写入者；不同目标可独立准备；在“意图已保存/副作用已发生/回执未落盘”三个位置崩溃后恢复，不重复合入；外部目标推进会触发重新验证；旧进程存活时不抢占。

完成条件：B 的候选验证与 C 的协调一起满足，才把 Self-heal 自动交付列为首批完成。不能只新增一个内存 mutex 就宣布跨入口安全。

### D — 变更索引、证据查询与发布关联（P1）

**目的：** 一次查询能追溯“为什么改、验证了什么、合入哪里、是否部署”。

开发项：

- 增加 changeId 与来源关联，以及必要的 SQLite 迁移；复用现有 migration 管线。
- Factory、Self-heal、Orchestrator 各自仍是真实状态来源；新索引是可重建视图，不设置第二个可随意 PATCH 的完成状态。
- 对事件消费使用来源事件 ID/版本去重，支持乱序与补偿重建。
- 关联 Release 已有候选 SHA、镜像身份、验证证据与回滚事实。
- 历史记录只回填可核实字段；缺失证据标记 legacy/unknown，不自动认证旧成功记录。
- 证据保留和分页沿用既有脱敏、大小限制及主体权限；截断必须明确提示，不隐藏验证所需的信息。

拟定只读 API：`GET /api/changes`、`GET /api/changes/:id`、`GET /api/changes/:id/evidence`。执行控制仍调用各原有受权接口。最终路由按现有 daemon 注册习惯落地。

拟定规格：`change-delivery-traceability`。

验收：重复/乱序事件不产生重复变更和错误状态；数据库升级保留历史；跨主体不能读取他人变更；squash 映射正确；一发布多变更及一变更多发布可追溯；无法核实的历史明确显示未知。

### E — Lab 变更视图与持久化策略（P1）

**目的：** 在已有任务/运维页面中解释当前进展和阻塞原因。

页面内容：

- 列表显示来源、意图、候选、验证有效性、交付状态、部署状态和当前原因。
- 详情显示验收标准、验证时间线、版本变化、审查问题、PR/合入记录、发布关联。
- 清楚区分“执行失败”“证据过期”“未运行”“待核对”；提供对应现有操作入口。
- 轮询保持筛选、滚动和展开状态；更新局部数据，避免整页跳动。
- 全部用户可见文案使用 useI18n；zh/en 同步，可复用 `ops`/`tasks` namespace。

设置：使用 `daemon_control` 和管理员设置 API 保存并发准备数、队列预算、重试预算、证据保留、通知策略；保存后后续调度立即使用。运行中的操作保留政策快照；撤销/暂停按原有控制语义生效。不得增加绕过验证的开关，不新增功能 env。

拟定规格：`change-delivery-lab`。

验收：刷新后偏好保留；保存策略不需重启；旧证据不会显示为当前通过；长列表更新不跳动；中英文叶子 key 一致；普通用户不能修改管理员策略。

### F — 成果分类与意图审查（P1）

**目的：** 让有效测试、性能、文档与 Skill 变更获得适当验收，不以“修改生产源码”作为价值代理。

开发项：

- 在活跃的任务入口增加 `feature/fix/test/performance/docs/skill` 成果分类；不修改废弃 Evolution 的分类器。
- 每类产出指定验收证据：功能/修复对应行为回归；测试对应可证明捕获的缺陷或代表性故障注入；性能对应可复现基准；文档/Skill 对应契约准确性、链接和可执行示例。
- 风险依据最终 diff、受影响契约和依赖决定，来源文章标签仅作为提示。修改测试框架、CI、验收或发布逻辑仍按敏感范围处理。
- 审查报告固定包含意图、验收映射、验证身份、真实缺陷、剩余不确定性和结论；区分有证据的问题与假设性建议。
- 保留现有独立审查及不削弱验收的规则。不得为了允许测试成果而允许删除断言、skip 用例或放宽门禁。

拟定规格：`change-outcome-validation`。

验收：纯测试变更在满足相应标准后可交付；纯文档变更通过其适用门禁；弱化测试的变更不会因分类为 test 获得低风险通道；来源低风险但实际改动权限/发布代码时按实际风险处理。

### G — 测量、缓存和按依赖调度（P2）

**目的：** 在正确性闭环稳定后减少重复工作。

先做结构化阶段指标：`prepareMs/installMs/buildMs/testMs/reviewMs/queueWaitMs/integrationMs`，再记录重复验证次数、冲突率、过期率、失败分类与成本来源。没有真实用量时写 unknown，区分估算与实测。

再根据基线选择优化：

- 复用 pnpm store，避免共享可写 node_modules/dist；缓存内容按锁文件、源码输入、工具链、平台及影响输出的配置寻址。
- 编辑期间按影响范围运行小套件；交付/发布时保留全部必需门禁。不能把命中缓存的构建等同于新候选 CI 通过。
- 用包依赖、共享契约和热点文件辅助调度；改不同文件也可能有语义冲突，路径不重叠不构成跳过验证的理由。
- 只有测量证明 checkout 是显著成本时才评估 sparse checkout；先验证 pnpm workspace 和 TypeScript project references 完整性。

拟定规格：`change-delivery-observability`，缓存另拟 `change-build-cache`，避免一个大规格绑住全部优化。

验收：耗时可按阶段解释；缓存输入变化必失效；损坏缓存回退到重新构建；并发不互相覆盖产物；优化前后用同一工作负载比较，发布证据要求保持一致。数值收益目标在取得基线后确定，不预先承诺百分比。

可能的关键路径是协调器与 Factory 现有实现的兼容，而不是页面开发。若阶段 A 证明可直接复用，减少抽象和工期；若发现新增跨机器协调需求，单独拆出，不能把单机 SQLite 锁描述成分布式锁。

## 7. 测试与验证矩阵

| 层级 | 必测场景 | 证据边界 |
|---|---|---|
| 纯函数 | 身份比较、政策失效、状态投影、风险分类 | 不证明真实 Git/平台行为 |
| 临时 Git 集成 | rebase/merge、无文本冲突的回归、squash 映射、脏工作区 | 用真实 Git，不 mock 成永远成功 |
| 多进程 | 同目标竞争、三处崩溃、旧进程存活、幂等恢复 | 用进程握手/屏障，避免依赖固定 sleep |
| 存储/API | 迁移、重复/乱序、分页、鉴权和主体隔离 | 所有查询与写入入口分别覆盖 |
| UI | 证据过期、状态分离、设置持久化、滚动保持、i18n | Playwright，明确实际执行范围 |
| 现有回归 | Factory 开发/交付、Self-heal、Release、质量门禁 | 保留既有 AC，不降低标准 |
| 现场 | 真实 GitHub 规则/CI/合入、实际镜像与部署恢复 | 软件测试通过不能替代现场验证 |

建议命令按每个 PR 实际文件收敛，最终必须包含适用的完整门禁：

```bash
pnpm exec tsc -b packages/core apps/daemon
pnpm run test:unit
pnpm run test:acceptance
# 对本次实际采集的 JUnit 做结果门禁，缺失套件不能冒充完整通过
node scripts/acceptance/acceptance-gate.mjs --results <本次结果目录>
pnpm run ci
```

涉及 UI 时补 `pnpm run build:web-console`、i18n 测试及对应 E2E；安排 E2E 前按仓库约定隔离/停止冲突的 Next dev 构建。新增测试文件必须进入真实 runner 范围，测试标题用 `[AC:<spec-id>#<AC-n>]`，禁止 skip/todo 占位。确需改 `packages/agent-loop` 时，另同步 SDK Skill，并在该包运行 test/build。

现场只使用已授权的测试仓库/环境；原有任务权限不因计划扩大。真实外部环境不足时如实记录未验证部分，不让 fixture 报告充当现场证明。

## 8. 迁移、上线和恢复

1. **增量记录：** 先增加身份和证据关联，旧数据保留 unknown；新字段兼容现有读者。
2. **旁路比较：** 对已有合法候选同时计算新判断，只记录差异；已有硬门禁始终有效，观察模式不是放行模式。
3. **按入口切换：** 先 Self-heal 的受控试运行，再接 Factory 只读关联，最后接 Release 和 Lab。每次切换确认只有一个写入者。
4. **故障演练：** 注入目标推进、runner 失败、进程中断和回执丢失；验证不会重复合并或丢证据。
5. **扩大使用：** 在兼容性回归通过并完成适用现场验证后扩大范围。

回退：暂停新调度，保留已创建候选、证据和操作意图，先核对进行中的副作用；界面/索引可回退到原有读取入口。不能回退为跳过验证的旧写入路径，不能逆向删除新 schema 或把已合入事实改成未发生。涉及数据库兼容和镜像恢复继续遵循现有 Release 规则。

## 10. 最终完成定义

任意一条受本计划覆盖的变更都能回答：谁提出、要满足什么、验证了哪个候选和基线、由哪个可信执行者验证、是否发生过失效与重试、最终合入哪个目标、是否进入某个已验证部署。

首批交付以 B+C 的行为测试和适用现场证据为准。仅增加类型、表、状态文案或计划文档不算完成；只跑静态验收扫描不等于行为验收通过。

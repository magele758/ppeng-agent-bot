# Bot schema upgrade and rollback drill

The reproducible fixture drill is:

```sh
node --test scripts/test/bot-migration-rollback.test.mjs
```

It creates a temporary detached worktree at `96d55dc`, compiles that revision's actual core binary with its own workspace packages, and loads the v24 SQL snapshot generated by that revision. Only synthetic temporary state is used; the checkout does not copy credentials or configuration from the working installation.

The drill verifies:

- Ownerless and hidden Bots, original private history, cron configuration and a transcript archive remain readable after upgrading to v25. Legacy history binds to the persistent installation identity and does not become a new login's private history or memory.
- Reopening the migrated SQLite file does not repeat schema versions, duplicate rows or change the installation identity. Foreign keys and integrity checks pass.
- New-version writes include a new private message and a queued Routine occurrence. The actual v24 binary rejects the v25 database before modifying it; its file hash remains unchanged. An in-place downgrade is therefore not supported.
- With writers stopped, checkpointed snapshots include SQLite, cron configuration and the fixture archive. The post-upgrade state is archived before restoration. Restoring the pre-upgrade snapshot into a separate temporary directory lets the v24 binary open and read the original state again. The post-upgrade writes remain intact in their separate v25 archive.

A successful snapshot restore does **not** make post-upgrade writes visible to the old release. Keep that archive and use a compatible release or an explicitly reviewed reconciliation process. Do not overwrite live databases, mix file sets from different snapshots, or replay unknown external writes during rollback.

This is a fixture-level stopped-writer drill. It does not prove an online backup procedure, a deployment rollback, completeness of a production installation's external assets, or safe automatic replay of new-version writes.

## 本阶段终点

**工厂在明确指定的实际环境运行 → 实际入口与运行版本已核对 → 一个获准真实项目由至少两台机器完成交付至 MERGED → 备份恢复、切换和回退完成演练 → 完整持续运行及发布证据通过 → 给出限定支持范围的发布就绪结论。**

两个部署概念必须分开：

1. 本阶段部署 `ppeng-agent-core` 工厂自身的前端、协调服务与必要运行依赖，并验证升级恢复。
2. 工厂交付真实项目的终点继续为 MERGED。该项目的业务上线、服务重启、数据库迁移、自动回滚与清理，仍需单独范围和验收。工厂恢复演练不能被用于执行业务项目恢复。

建议首个支持档位：Linux 常驻协调节点，优先复用现有 Docker Compose 的 daemon/web 制品；持久状态使用已支持的单实例方式，通过受限 SSH 连接 Ubuntu1、Ubuntu2 的宿主执行器。协调与执行可以同主机，但资源与任务归属必须核对。SQLite 保持单个有效写入协调者，不默认开启多副本或高可用。Docker、SSH、宿主凭据与发布能力必须随实际部署验证，不能从开发机工具可用推断容器具备这些能力。

首个真实项目选择已有、由用户控制、可做小范围任务的项目。至少两个有真实项目价值的小任务，每台机器各一个；有明确需求、可失败验收和正常 CI。不能用 sum/product 玩具仓库再次代替真实项目验收，也不能为制造 CI 故障损坏业务 main。

不默认把 `ppeng-agent-core` 本身作为首个自动修改项目，避免工厂修改自身运行环境产生递归发布。若选它，必须另行明确隔离工作区、运行候选、目标分支与防自修改范围。

## 性能与持续运行口径

沿用 `scripts/bot-release/workload.v1.json` 及现有完整协议，不改原已批准门槛：

- 标准环境独占 4 vCPU、8 GiB、已核实 SSD，使用仓库规定 Node；记录实际限额、存储与运行身份。不能用更高配置、未知介质或受竞争环境冒充匹配。
- 50 Bot、10 活跃 Bot，一个 Bot 10 万条、共 100 万条未预压缩历史；20 客户端合计 40 次读请求/秒，读分页/检索/状态为 50%/30%/20%。
- 顶层工作 2 次/秒，人类/Routine/委派/Room 为 40%/20%/20%/20%；委派和 Room 各至多三个下游，审批延迟、输入/输出/工具及产物大小均沿用完整协议。
- 完整性能测量预热 300 秒、测量 900 秒，最后 120 秒排空。延迟从计划发起时刻计算，包括客户端排队；浏览器首屏用真实浏览器测量，不能用分页接口耗时代替。
- P95：分页/状态/接收各 ≤500 ms，检索 ≤1,000 ms，首屏 ≤2,000 ms。
- 浸泡预热 1,800 秒、连续测量 86,400 秒；每小时 60 秒、20 顶层工作/秒突发，其中热点分布沿用原协议。每 10 秒采集进程树 RSS，半小时窗口 P95 ≤首个完整窗口的 1.2 倍；同半小时相位的队列长度和最老等待时长 P95 不得连续三个小时同时严格上升。
- 固定种子候选故障序列每次至少 10,000 条，连续三次通过并有真实杀进程重启证据。目标环境完整浏览器连续三次无重试通过。
- 每个拟支持真实模型至少三次完整记忆/压缩验证：200 轮、12 次压缩、100 条核对事实，关键召回 100%、其他 ≥95%；真实软件读写、审批和未知副作用核对单独验证。

受控模型/软件的完整负载用于容量和长期稳定性；真实模型及真实项目另行验证，不能互相冒充。性能与浸泡串行执行，避免互相抢占验收资源；使用隔离的合成验证数据，不拿真实用户聊天充当百万历史种子。真实故障演练与连续正常浸泡分开记账。

完整窗口中断、漏采、预算不足、子进程异常、实质配置或制品变化，都不能靠拼接时间和重复尝试掩盖。保留失败记录，明确剩余预算与重新运行范围。运行制品、关键配置或协议实质变化后重新完成受影响验证；纯报告补充不能伪造候选变化，也不能用报告版本替换实际运行版本。最终结论指向已验收的固定候选，不要求为了更新文字报告而重建运行制品。

## 推进次序与放行

1. 用户确认 40 条标准；保持既有规格不变，逐条先失败测试后实现。
2. 冻结资源、权限与预算清单。补齐部署身份、依赖预检、证据校验及恢复流程，先在隔离环境验证拒绝路径。
3. 将固定候选部署到实际主机的隔离候选入口，核对版本、鉴权、双机连接、持久化和浏览器完整流程，不立即切换既有真实用户流量。
4. 用获准真实项目完成双机小任务与恢复边界；业务交付仍只到 MERGED。独立核对 PR、合入者、候选/合入提交、原工作区、任务归属与机器容量。
5. 完成备份还原、迁移兼容、升级及回退演练；再按固定协议串行执行完整性能、故障、真实模型/软件和 24 小时窗口。未测支持项保持未验收。
6. 纵向审查“实际入口 → 鉴权 → 群任务 → 存储/归属 → 双机执行 → GitHub → 结果与告警 → 升级恢复 → 发布证据”；发现问题先补失败回归并修复，重新运行受影响门禁，不删除或弱化标准。
7. 候选门禁通过且切换范围获准后，切换工厂实际入口，独立验证运行制品、持久数据及功能。回退只在确认的工厂范围与安全条件内进行；条件不满足即停接新工作并待决。
8. 汇总实际运行和恢复证据。代码 PR 的合并不代替部署验收；部署也不代替发布就绪。全部标准通过后才标记 implemented，给出可运行版本、项目、模型、机器范围及已知限制，不宣称全产品开发完毕。

已有 `bot-release-readiness` 仍按原三条标准单独核对，不能仅因新增这份规格或静态标签齐全就改为 implemented。缺少真实环境、长时证据或原始产物时明确输出未就绪，不默认豁免门禁。

# 并行完整验证

本次只调整执行安排。Quick 的两分钟上限、每两小时完整检查、手动验证、全部验证范围、质量阈值、变异基线与发布要求均不改变。部署继续后置，原现场验收保留。

## 执行关系

- `unit`：从原 `test:unit` 范围自动发现普通功能测试，一次执行产生功能结果与 V8 覆盖率。
- `formal`：同一发现范围内的直接 Formal 调用者与原 Formal 入口的四组回归测试。随后执行完整 Formal 模型、真实进程、故障注入、反向控制与规定重复检查；四组已经运行的回归不再重复执行。
- `sdk`：独立执行 SDK Vitest 覆盖率，保留全部测试。三类任务无需互相等待完成。
- `crap`：等待三个任务成功，核验并合并覆盖率产物后评分；不重新启动单测或 Vitest。
- 浏览器/HTTP/集成、构建/包消费/能力契约和四片 Mutation 继续独立执行，完整验收与发布汇总等待全部必须结果。

普通 `pnpm run test:unit` 和 `pnpm run test:formal` 入口仍保留原完整行为。拆分只用于 CI；Node 测试各有唯一所属任务，新增匹配测试自动进入分工。测试命令无法识别、模式无匹配、归属重复或必要范围缺失时失败。

## 产物与失败处理

每个覆盖率包包含候选提交与树、源码及编译产物摘要、Node/平台/路径、运行批次与尝试次数、测试文件清单、各文件摘要、独立 JUnit、耗时及首轮失败记录。消费者先逐项验证，错误候选、过期批次、文件不完整或损坏、清单不符均拒绝使用。三个任务的 JUnit 名称不同，验收汇总不会相互覆盖。

Formal 保留原严格证据复用机制及完整输入绑定；同输入的规范探查可以复用，显式子集、故障和规定重复仍实际运行。调用入口统一使用同一 Node 和环境，避免仅因入口差异产生不必要的重复。模型检查仍是有界证据，不扩大为全系统证明。

失败任务保留已有证据；其他独立任务继续执行。任何必须任务失败、取消、超时或缺少证据都不能通过完整发布汇总。真实模型 smoke、Compact A/B、Harness 的既有适用规则不改变，实际失败/跳过仍可见，不能宣称未执行的模型质量已通过。

## Quick 与耗时口径

Quick 保留原有审查指纹、工作区编译、控制台类型、权限/审批、CI策略与静态验收，新增存储迁移、引用和分叉短回归。执行器上从任务开始至结束必须在120秒以内，包含准备、安装、检查及证据上传；平台排队单独计时。内部检查仍采用原90秒预算。超时不得通过，普通合并要求当前版本 Quick 与 review 均通过。

记录每个任务及步骤的实际执行时间，完整运行总历时单独报告；不把并行任务时间相加。不将本地暖构建、局部证据复用或取消样本当作完整冷运行提速证据。

验收规格：`acceptance/ci-parallel-validation.yaml`。发布依旧要求实际候选完整通过及原有包/镜像消费和启动检查；软件通过不等同于现场40条验收完成。

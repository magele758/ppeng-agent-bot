## 已确认范围与完成定义

第二阶段形成一条完整纵向链路：**批准的需求 → 群/Lab派单 → 就绪检查 → 指定机器隔离工作区 → 失败测试 → 开发 → 必需测试 → 同机独立自审 → 有限修复循环 → 本地READY → 证据回群**。

一个任务由同一机器的同一Bot负责到READY。开发默认关闭，项目单独授权；只读任务继续执行原有只读约束。模型和工具由Lab选择，使用已安装的可用工具，不硬编码附件中的供应商和模型。

READY表示对应**本地提交**的批准验收、必需测试和完整评审均已满足，并保存工作区供复查。它不表示远端CI、合入或部署完成。READY后没有运行进程则释放执行容量，但保留分支、工作区和证据；这些保留产物需有磁盘容量检查，不自动删除。

本阶段不包含推送队列/推送锁、远程推送、创建或合并PR、迁移分支直接快进发布、部署与回滚、已有服务重启、自动删除分支/worktree。后续阶段再定义这些发布与交付能力的验收。此次项目自身的实施PR流程与被实现的工厂运行权限是两件事，确认第二阶段并不自动解除工厂发布限制。

附件是目标模式与经验材料，其中“直接推送合入”“私信决策者”等操作文字不是本轮用户授权。建议保留其同机归属、默认6轮、完整分段评审及安静巡检原则；待决先落Lab与原工厂群，外部私信通道暂不接入。

工作区隔离只防止普通文件冲突，**不等于进程权限隔离**。编码工具、依赖生命周期脚本和测试均可执行代码，因此执行边界必须覆盖它们：宿主凭据、Git公共元数据、其他任务与服务不能因开了worktree就默认可写。运行时选择何种隔离机制留给工程实现，但不支持所需边界的机器必须就绪检查失败，禁止静默无隔离运行。模型连接仅注入该工具所需凭据，结果继续脱敏；不将GitHub推送或宿主SSH凭据交给编码任务。

必需检查由项目策略预先指定。例如本仓库为类型/构建、全量单测、验收、CRAP及受影响的HTTP/E2E；SDK变更仍遵守其同步文档与测试构建契约。基线已知失败必须逐项有依据，不能只以失败计数不增加认定通过，也不能由任务自己改豁免或门禁来过关。

同机独立自审指同一机器另一次评审执行，核对需求、验收与完整diff；可以分段，但需记录覆盖清单及各段版本。机器可核对证据完整性和有效性，不把模型输出CLEAN当作代码绝对正确的证明。P0/P1未关闭不能READY，P2等非阻塞项必须显式披露。

## 实施与验证顺序

1. 负责人已确认，将规格改为approved。按33条逐项建立带验收标签的失败测试，保存失败原因；不以占位测试或环境失败代替。
2. 先连通受控开发授权、任务快照、就绪检查和远端隔离；再做单任务开发至READY，最后扩展并发、依赖、恢复和巡检。每步沿群/Lab到远端再回状态与证据验证。
3. 重点注入越权写入、重复提交、断线、重启、取消、旧回执、评审缺段/503、轮次耗尽与证据过期。先看到失败再修复。
4. 跑第一阶段23条及项目适用的自动化回归；纵向review权限、调度、远端、产物、回群与界面，不只检查新增模块。
5. 用户指定至少两台真实机器上的专用试验仓库。每台走完真实改码、测试和自审；整体试跑至少出现一次真实阻塞→修复→重测→复审，再验证重复请求和断线/临时协调服务重启。测试仓库构造确定性问题，真实模型完成开发/评审，不用模拟响应替代机器验收。
6. 独立核对机器身份、工作区/基线/结果提交、门禁与评审记录、实际进程和容量；记录远端分支、原检出及已有服务未变化。保留所有试跑产物供确认，全部满足后再标implemented。

第二阶段预计主要工作在远端执行边界、长任务恢复和证据门禁。不能简单把第一阶段的操作列表加上“运行shell”完成升级。

## 已确认的边界

- 终点为本地READY；发布、合入、部署与自动清理后置。

- 同机开发与独立自审，工具及模型走Lab配置；不要求当前安装所有编码CLI。
- 真实试跑使用专用仓库，至少两台机器；现有业务仓库与服务保持原状。
- 33条标准已确认；实现期间没有删除或弱化标准，新增行为变更仍需重新确认。

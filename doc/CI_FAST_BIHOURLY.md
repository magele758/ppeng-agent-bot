# 快速合并与每两小时完整验证

2026-10-20，负责人确认采用 `acceptance/ci-fast-and-bihourly-gates.yaml` 的8条标准，再修复、review并合并所有未合并PR。此政策替代原 `ci-gate-speedup` 的逐PR完整阻断条件。原9条原文及批准和失败记录保留；三旧三新性能统计未验收，不宣称30%中位数提速已通过。

每个PR版本以及main提交自动执行 **Quick gate**：作业总时限2分钟，内部实际验证预算90秒，为checkout、Node和依赖准备预留时间。运行改动函数的圈复杂度（超过30即失败，不等覆盖率）、工作区类型构建、Lab类型检查、四套形式源码审查指纹、短时审批/权限及CI策略回归、验收映射检查。没有增加重试、放宽阈值或将quick结果伪装为完整验收。平台排队另计，超时和证据缺失不得当作通过。

与 Quick gate 并行的 **Core unit tests** 跑核心库、可嵌入循环和控制台单测，不收集覆盖率，不跑浏览器、浸泡或变异。PR 的等待时间是两者中较慢的一个，不是相加，也不是完整验证。

**Full validation** 在合入 main 时立即启动，并仍在 UTC 每个偶数小时的第17分钟运行（每两小时）。也可手动在指定分支执行。完整复用原 release-gate，但云端不再跑浏览器 E2E。HTTP 回归和集成仍在。浏览器用例留在仓库，用 `pnpm run test:e2e` 在本地执行。相同分支完整任务不取消正在运行的任务；更新的排队候选会替换更早的排队，证据按 run/attempt 隔离。定时器由 GitHub 调度，可能因平台负载延迟。

CI的手动入口仍可执行完整验证或冻结旧顺序基线，均不替代当前PR的Quick gate。独立Mutation仍可手动执行，完整变异的定时责任统一归入两小时验证。镜像不再因普通push/PR重复触发完整门禁，仍保留计划与手动发布，发布前原完整验证和容器冒烟必须通过；npm/tag发布的完整门禁保留。

分支保护要求当前版本的 **Quick gate**、**Core unit tests**，以及 PR 上的 **Main full health**。主分支最新完整验证失败时，Main full health 拒绝合并；这个 PR 头已经有一次成功的完整验证时允许合并，避免修复被自己挡住。快速门禁在主分支变红时仍会执行。完整验证失败保留实际候选、日志与制品，不因随后的 quick 绿灯清除，也不能把已合并说成发布就绪。现场部署验收仍后置。

完整浏览器入口为 `pnpm run test:e2e:full`：每个 spec 文件启动独立的临时 daemon、Next、数据库与鉴权 token，避免跨文件累计 Bot 耗尽产品的 50 个名单上限。原上限不变，全部文件均执行；任一文件失败则整体失败，JUnit 和截图/trace 按文件分别保存。指定用例调试仍可使用 `pnpm run test:e2e <file>`。

HTTP soak 驱动的观测账本以 100ms 为窗口提交事务，保留 SQLite FULL 同步，不再为每个读取状态变更单独同步磁盘。仅驱动自身的记录合批；daemon 的持久化、负载、计划发送时间、端到端延迟统计、遗漏时隙检查与性能门槛保持不变。最终报告写出前提交剩余记录。

### Lab 性能回归

每个 PR 的必需检查 **Main full health** 会构建候选版本，在临时 SQLite 数据库上测量后台调度、会话启动和首页请求。合入 main 后以及每两小时的完整验证，在 **HTTP regression** 中运行同一基准。失败指标显示在 Actions 的运行摘要里，`lab-performance` 制品保留候选提交、各项实测值和预算 30 天。单个请求的最长耗时单独判定，即使其他请求很快，一次长时间卡顿也能触发失败。

在装好依赖的独立检出中运行 `pnpm run bench:lab` 会构建并测试生产版。如需同时测量实际页面出现和输入框可用的时间，安装 Playwright Chromium 后运行 `pnpm run bench:lab --browser`。已构建的同一候选可直接执行 `node scripts/lab-performance/run.mjs`。结果写入 `test-results/lab-performance/report.json`。

| 场景 | 固定负载与判定 |
|---|---|
| 空闲后台 | 64 个 Bot、256 个已结束目标、512 条执行记录、512 份每日复盘。预热后分别轮询 3 次，统计完整历史读取数、SQLite 变更数、中位耗时和最慢一轮。另引入真实待办，验证调度仍能处理。 |
| 会话首发 | 普通会话和 Bot 各创建 5 个新会话，经真实流式发送入口，测到本地模型替身收到请求的中位耗时。预热后桌面工具重复连接的预算为 0。 |
| 模型请求前缀 | 两种入口分别执行两次受控工具调用并跨越会话阶段，比较发给 Responses 服务的请求设置和已有历史，前缀漂移预算为 0。该指标能离线捕捉导致缓存失效的请求变化，供应商实际命中率仍取自真实用量日志。 |
| 首页 | 在生产版 Next 和同一个有历史数据的 daemon 上，轮询后台的同时，经 Lab 请求首页、登录状态、服务就绪和已有 Bot 的历史。10 轮正式样本检查各接口 P90 和单次最大值。本地浏览器模式另用 6 个新浏览器上下文，只输入一次草稿，等目标 Bot 打开后验证文字仍在，另测指定历史正文可见时间，并检查连续回复的实际段间距。云端另运行 Bot 打开与手动切换时的草稿归属单测。 |

耗时门槛和计数门槛在 [budgets.json](../scripts/lab-performance/budgets.json)。基准遇到异常、观测不全或超预算时返回非零退出码。调整负载或门槛时，一起保留变更前后的实测值，便于审查时判断它是否仍能拦截已知退化。

首版校准时，同一套合成负载在旧版 `7626bcf7` 的三轮空闲轮询中触发了 192 次目标写入和 2,688 次每日复盘写入，修复版均为 0。本机在 3 次独立的 Node 22 浏览器基准中，首页接受输入且打开后草稿仍在的中位数为 210–248 ms，恢复指定 Bot 的中位数为 232–288 ms。单独把一次登录响应延迟 2.25 秒时，各接口 P90 仍低于 45 ms，单次最长耗时达 2,275 ms，触发了 2,000 ms 的门槛。

热态中位数和接口 P90 还会与首次通过的 GitHub Ubuntu x64 / Node 22 记录比较。实测同时比参考值高 50% 且多 20 ms 时，摘要和 GitHub 检查会提前警告。超过硬上限仍会阻止合并。参考运行的普通会话与 Bot 首发中位数为 24.9、33.1 ms，首页、登录、就绪、近期消息的 P90 为 20.89、47.36、52.35、47.41 ms。[首次云端基准](https://github.com/magele758/ppeng-agent-bot/actions/runs/44502280252)
